# GEO 产品深度体检与开发方向（2026-09-26）

## 1. 这份体检回答什么

本报告针对用户提出的产品问题：GEO 目前像半成品、界面不好用、分类和功能排布混乱、下一步开发方向不清楚，以及如何让系统更智能、更有用。

仓库里的 `AGENTS.md`、`README.md`、产品门矩阵和历史审计是工程约束与证据来源，不是本次产品目标本身。它们要求产品门、身份、存储和验证保持诚实；本报告在这些边界内重新判断产品价值和优先级。

审计基线：`codex/geo-ui-layout` @ `4cb0725`。第 1–11 节记录的是施工前基线；后续实际施工见第 12–13 节。

## 2. 结论

GEO 现在不是“功能太少”，而是同时存在三种断裂：

1. **价值断裂**：监测、洞察、内容、市场、资料各自有能力，但“发现问题 → 解释原因 → 采取动作 → 发布 → 复测”的闭环还不是一个可信的产品主线。
2. **语义断裂**：同一个“提及率、覆盖、健康、认知、缺口”在不同页面和接口中有不同口径；空数据、依赖不可用、没有结果常被压成空值或 200 响应，用户难以判断结论是否可信。
3. **架构断裂**：UI 通过产品门继续使用 legacy v1 + SQLite；同时仓库已经有 Product-owned PostgreSQL 的 v2 纵切片。两套运行时和数据面没有迁移切换计划，继续在两套路径上加功能会形成双真相。

因此，下一阶段不应继续增加菜单、卡片或“AI 功能”。应该先把 GEO 收敛成一个**AI 可见度行动系统**：

> 对一组真实客户问题，持续观察各模型如何回答企业；用可追溯证据解释差距；给出最值得执行的动作；登记发布；用同一批问题复测并显示变化。

若这条链不能稳定回答“发生了什么、为什么、做什么、做完是否变好”，新增功能只会增加噪音。

## 3. 当前状态评分

| 方面 | 判断 | 依据 |
|---|---|---|
| 后端能力广度 | 中上 | 约 140 条 v1 能力、监测/蒸馏/洞察/内容/市场均有代码；但 5 个路由确定返回 501，另有外部依赖导致的 500 |
| 核心业务闭环 | 偏低 | 计划、发布、复测已有接口，但指标与证据尚未统一，动作效果不能稳定回流到问题级结论 |

## 4. 已经有价值的部分

- 监测对象、任务、回答、引用、情绪、竞品、行业、信源和趋势已有相对完整的接口基础。
- 问题池 → 知识缺口 → 内容计划 → 内容生成 → 发布登记 → 复测这条概念路径已经存在，且内容生成可展示来源、未验证声明和事实检查结果。
- 产品门、会话身份、按账号分柜、危险操作二次确认等边界意识比普通半成品项目强。
- 监测和认知分析已经保存了模型原话与证据，不需要再造一套“看起来像 AI”的假数据层。
- `docs/GEO_CONTENT_SELECTION_ALGORITHM.md` 与真实资料评估已经发现了关键事实：Chunk 级召回、版本包含度去重、相对阈值和分层预算比继续堆 prompt 更重要。

这些是重构时应保留的基础，不应该推倒重写。

## 5. 最重要的阻塞与风险

### P0：先解决双运行时和双真相

当前 UI 通过 `packages/geo/src/geo-advisor/geo-api.ts` 请求 `/api/product/geo`，产品门再把请求映射到 `apps/api/app/api/v1/*`。这意味着主业务仍然落在 legacy SQLite Store；`apps/api/app/api/v2/product_monitor.py` 的 Product-owned PostgreSQL 纵切片只覆盖一个 monitor-run，未成为主链路。

这不是单纯的技术债。未来如果监测配置、运行记录、回答证据和报告分别存在两套存储，用户会看到两个互相矛盾的“最新状态”。

**决定：**冻结 v1 为兼容面，不再往 v1 增加新的业务概念；先把 v2 做成一条完整的 `配置 → run → observation → analysis → result` 主链，再按领域迁移。每迁一个领域必须有唯一 owner、迁移状态、回滚/前进策略和 UI 切换开关。

### P0：修正账号隔离和后台任务的作用域

审计发现：

- `GeoInsightReports`、`GeoDimensionSynonyms` 没有 `tenant_id`；最新报告是全局取最新，重置也可能清理全局报告。
- `services/intelligence/queue.py` 的队列消息只有 `evidence_id`，没有 tenant/deployment/enterprise；worker 和恢复逻辑依赖当前进程上下文。
- `snapshot()`、`wait_drained()`、自动报告计数是全局的，账号 A 的任务可能读不到或误读账号 B 的证据。
- 媒体目录是全局目录；`knowledge/reset` 里 Qdrant 地址硬编码为 `127.0.0.1:6333`，没有使用已支持的 `GEO_QDRANT_URL`。

在这些问题修完前，不应对外承诺“账号分柜已经完成”。

### P0：建立单一指标和状态模型

必须先冻结这些业务定义：

- 提及率、推荐率、引用率、SOV、首次出现句序分别是什么分母、时间窗和主体范围。
- “无数据”“未配置”“依赖不可用”“运行中”“失败”“没有命中”分别如何表示。
- Knowledge Gap、Evidence Gap、Content Gap、Execution Failure 是否是四种不同状态。
- 一次监测 run、一次问题回答、一条证据、一项行动和一次复测如何关联。

现在多个接口会以 HTTP 200 + 空值或 `data.error` 表示依赖失败；这会把“系统坏了”渲染成“企业没有数据”。先统一契约，再改 UI。

### P1：完成真实内容选材，而不是继续加生成选项

生产代码 `services/content/__init__.py::_relevance_order` 仍然主要使用 n-gram 文档排序；真实正式资料评估把 A3（排序 → 包含度去重 → 代表选择 → 非重复补充 → 相对阈值 → Context Pack）标为唯一全过方案，但 `GEO_CONTENT_SELECTION_REAL_EVAL_v1.md` 仍是 `NOT FROZEN / ENGINEERING BLOCKED`。

这直接决定“智能内容”是否有用。没有 Chunk 级去重、覆盖和“不足就承认”，模型只会更稳定地写出看似流畅但资料混杂的文章。

**完成门：** 固定离线评估集、Context Pack 契约、来源层级、无命中行为和最小证据字段；在真实企业资料上通过命中率、重复污染率、无资料误选率和问题覆盖率后再启用。

### P1：把未完成能力从“已放行”中拆出来

产品门当前允许访问整张 legacy v1 面，但以下能力确定返回 501：

- `/collect/crawl`
- `/analyze/diagnose`、`/analyze/reports/{id}`
- `/keywords/expand`
- `/eios/export/knowledge-index`

这些路由目前没有相应回归测试。能力清单必须改成四态：`implemented`、`experimental`、`blocked_by_dependency`、`not_started`；产品门只放行 UI 真正能完成且有明确状态的能力。

### P1：把后台作业从进程内状态变成可恢复任务

`asyncio.create_task`、进程内 APScheduler 和内存队列在重启、多 worker、长任务失败时会丢状态或重复执行。自动配置、监测、解析、报告和自动生产都应该有持久化 job/task、幂等键、租户作用域、重试上限和恢复状态。

### P1：重做 UI，而不是继续拼卡片

当前 `main.tsx` 虽然已经收敛为六个一级工作区，但代码明确写着“只把已有卡片排成一条业务路径”；容器仍叫 `.geo-legacy-surface`。`index.css` 有约 77 KB、519 行，包含重复主题、旧 `.geo-rail`、未使用的 `.geo-v2-*` 和大量 raw HTML 样式；`packages/ui` 的 Card/Badge/Table/Tabs 等组件几乎没有被业务页面使用，前端实际大量直接写 `<button>/<input>/<select>`。

当前导航还把持续工作区、一次性工具和报告放在同一层：AI 对战、知识库同步、自动配置、阶段报告、认知健康、客户认知地图的颗粒度不同；“认知洞察/认知健康/客户认知地图”语义重叠；“资料总揽”有命名错误；中英文 eyebrow 与中文业务文案混用。

UI 的目标应是让用户在两次点击内完成“结论 → 证据 → 动作”，而不是让用户猜接口属于哪个页签。

### P1：明确 Host 会话模式

`useProductHostSession()` 在顶层直开时把 `window.parent === window` 视为已连接，但 transport 仍是 `/api/geo/api/v1`；文档已有实测：直开页面会收到 SPA HTML，被当成 JSON 后显示成“请求失败（200）”。应明确产品只允许 Host iframe，或提供真正可用的 standalone 模式，不能静默回退到错误的 BFF 地址。

## 6. 推荐的产品模型

GEO 的核心对象不是“页面”，而是一个可复测的 **Visibility Case（可见度案例）**：

```text
目标主体/产品
  + 一组客户问题（按购买阶段、场景、行业和意图分组）
  + 一组监测模型与时间窗
  + 一次观察 run
  + 每个问题×模型的原始回答、证据与置信度
  + 一个差距判定（知识 / 证据 / 内容 / 执行）
  + 一个行动及其发布记录
  + 发布前后同口径复测
```

以后所有页面都围绕这条对象链展开：

1. **总览**：本周期发生了什么；最值得做的一件事；数据新鲜度与可信度。
2. **监测**：问题集、模型、运行状态、原始回答和引用。
3. **洞察**：按问题/场景解释“为什么没被提到”，证据与置信度并列。
4. **行动**：按影响 × 证据强度 × 执行成本排序的行动队列。
5. **资料**：企业事实、原始素材、版本、来源和同步状态。
6. **市场**：只有能改变问题集或行动队列的竞品信号和收录结果。

AI 对战是监测中的采样工具，报告是洞察的导出形式，自动配置是 onboarding 向导，向量化是后台状态，重置是管理员设置。它们不应占据持续业务导航的位置。

## 7. 让系统真正“更智能”的顺序

### 第一层：感知可信

- 问题集由用户目标 + 行业 + 购买阶段生成，去重并可人工编辑。
- 每次 run 保存模型、时间、问题版本、原始回答、提及位置、引用 URL、证据新鲜度和解析状态。
- 所有指标显示分母、时间窗、样本量和“不可判定”原因。

### 第二层：解释可追溯

- 使用 A3 Context Pack，按 Chunk 召回、同版本包含度去重、分层预算；没有相关资料就显示“资料不足”。
- 将差距分成：知识不存在、已有知识但未被引用、内容未发布/未被收录、运行或依赖失败。
- 每个结论都能打开原始回答、证据片段、来源、版本和判定规则。

### 第三层：行动有回报

- 行动分数 = 预期影响 × 证据强度 × 时效性 ÷ 执行成本；显示计算分解。
- 一键从差距创建内容计划或资料补齐计划，但不自动替用户发布。
- 发布登记使用同一个资产 ID；复测必须复用原问题集、模型集和时间窗，并写入前后基线。

### 第四层：系统会学习

- 记录“哪类问题、哪种资料、哪种内容结构、哪种发布渠道”带来变化。
- 等效果样本足够后，再做经验推荐和自动选材；在此前不要做无评估的“智能排序”。

## 8. 90 天开发路线

### 0–2 周：可信度收口（停止新增功能）

- 生成唯一能力清单：路由、实现状态、依赖、UI 入口、测试覆盖、成本和 owner。
- 冻结指标、状态和错误契约；把 501 与外部依赖错误从“空数据”分离。
- 修复报告、同义词、智能队列的租户作用域；媒体按柜存储；reset 使用配置化 Qdrant。
- 修复 Host-only/standalone 明确模式；补齐 `.env`/Foundation 依赖/CI profile，让默认验证命令可复现。

**验收：** 账号 A/B 的 run、报告、词典、媒体、队列进度完全互不可见；所有空态能区分“无数据”和“系统不可用”。

### 3–6 周：一条主链跑通

- 以 Product-owned v2 为主路径实现 monitor configuration → run → observation → analysis → result。
- UI 只做一个“可见度案例”工作台：问题集、最近 run、回答明细、差距、下一动作。
- legacy v1 只读兼容；禁止在 legacy 路径新增业务语义。

**验收：** 新账号从零配置到一次可复测 run 不超过 10 分钟；一项差距两次点击能看到证据并创建行动。

### 7–10 周：智能选材与内容闭环

- Freeze A3 Context Pack 和真实企业评估集。
- 把报告、问题池、监测回答、资料和内容资产接入同一条行动队列。
- 生成结果必须显示引用片段、未验证声明、资料不足和发布前质量检查；发布/复测写回同一资产。

**验收：** 无资料问题不凑数；重复版本不占满 Context Pack；复测能显示问题级变化和样本量。

### 11–13 周：市场与规模化

- 只保留会改变问题集或行动队列的市场信号；链接收录作为行动效果证据。
- 持久化 job/task、租户锁、重试、恢复和审计；再考虑自动闭环。
- 将剩余领域按同一 migration template 从 v1 迁到 v2。

**验收：** 重启和多 worker 不丢长任务；同一幂等键不会重复扣额度或重复生成。

## 9. 明确暂缓的事情

- 不再增加一级菜单、孤立 dashboard 或新的“AI 对战/报告”变体。
- 不在 A3 评估冻结前继续加 prompt 开关、模型数量或向量检索参数。
- 不把 501 路由包装成漂亮的按钮。
- 不扩展 GEO 的第二套知识语义或复制 Foundation canonical 数据。
- 不在租户隔离和任务持久化修复前上线自动生产、自动发布或跨账号报告。

## 10. 本轮验证记录

- `npm run check:ui`：通过；Vite 产物 JS 约 512.69 KB、CSS 约 115.92 KB，并有 chunk 大小警告。
- 带 Foundation 跨仓包路径的 `.venv/bin/python -m pytest -q`：303 passed、5 skipped、6 warnings。
- 不带跨仓包路径时：8 个测试因 `eios_policy/eios_auth/eios_contracts` 不在项目依赖中失败，说明默认验证命令不完整。
- Product Door 冒烟：大量 legacy 读路由可达，但 5 个 501 stub、若干外部依赖 500 和 PostgreSQL slice 默认跳过；“全路由放行”不等于“产品可用”。
- `docker compose config --quiet`：因 `apps/api/.env` 不存在而失败。

## 11. 最终判断

这个项目值得继续做，但开发目标要从“把剩余接口和卡片接上”改成“让每个结论都能解释、每个动作都能复测、每个账号都能隔离”。先收口数据和主链，再做选材智能和视觉重构，GEO 才会从半成品工具箱变成可持续使用的工作系统。

## 12. 分析整合施工记录（2026-09-26）

在上述审计结论基础上，已先落地前端低风险收口，未改监测对象管理组件、监测对象接口或计数逻辑：

- `GeoMonitorAnalytics` 将六类分析接口并行读取，默认输出最多三条带样本范围的优先判断；完整六类明细收进“按需核对”区域。
- 判断按“被看见 / 可信度 / 决策差距”组织，并提供到问题池、知识缺口、企业资料或详细分析的动作入口。
- 客户认知地图复用整合分析页面；当前批次覆盖和历史语义维度各自标注范围，未判定与未评估不渲染成 0 分。
- 监测报告明确区分模型原始回答（Observation）与企业事实结论；主体未确认或缺少依据时不升级为事实。
- Client 内 `/app/geo` 已打开并验证整合页面：有 562 条有效回答时能生成三条判断；证据核验可见“10/48 抽检、知识依据不可用”等真实状态。

验证：`npm run check:ui` 通过，`git diff --check` 通过。构建仍有 JS chunk 大于 500 KB 的既有体积警告；本轮没有引入新后端路由或数据库迁移。

## 13. 内测演示数据施工记录（2026-09-26）

由于真实企业资料和认知洞察接口当前可能为空，本轮增加了**显式开关式**前端演示夹具：

- Client GEO 顶部新增“内测演示 开/关”，状态保存在当前浏览器的 localStorage。
- 开启后仅替换企业资料、认知健康、认知洞察和证据抽屉的展示数据；监测对象、真实监测回答、产品门接口和数据库均不写入。
- 每个演示页面都显示“内测演示数据 · 虚构内容，不进入正式统计、报告或证据链”。
- 演示模式下“生成补充计划”“重新评估”“导出 Word”等写入/导出动作被拦截，避免把 fixture 误写入真实工作区。

7. **内容智能上线门。** 推荐先扩大真实评估集并冻结 A3 Context Pack（排序、包含度去重、代表选择、非重复补充、相对阈值），再把监测缺口、竞品差距和核验结果作为带证据的生成输入；事实门继续禁止模型用常识补企业事实。

本轮在选择了具体主体时，把该主体的规范企业名传入生成、评分、改稿和质量检查；选择“全部”时继续由后端按当前账号自动识别企业，避免猜某一个主体。页面上的主体说明因此与实际生成上下文一致。

验证：`npm run check:ui`、`git diff --check` 通过；生成接口继续使用已有 `company_name` 合同，没有新增数据写面，监测对象管理文件保持零差异。

## 137. 2026-09-27 决策阶段问题数与回答覆盖统一主体范围

认知洞察的阶段覆盖接口已经按主体过滤回答，但问题池的 `question_count` 仍把账号里的其他品牌、产品或竞品问题算进来，导致同一阶段的分子和分母不是同一范围。

本轮让阶段问题数只统计当前主体绑定的问题；选择“全部”时只汇总启用中的企业品牌主体，未绑定的历史问题不再冒充当前品牌样本。同步补充主体范围回归断言，避免以后只修回答分母而漏掉问题分母。

验证：主体范围测试通过；全量 `330 passed, 5 skipped`，`npm run check:ui`、`git diff --check` 通过，监测对象管理文件保持零差异。

## 138. 2026-09-27 模型对比明确为带主体标签的一次性即时实验

模型对比页此前只说明“不写入监测统计”，但没有显示它针对哪家企业。多品牌工作区里，用户容易把一组原始回答误认成当前监测主体的正式结论。

本轮让模型对比复用 GEO 的监测主体选择器；请求可携带所选品牌，后端只校验并返回范围元数据，不把 Quick Check 写入监测证据或改变监测任务。结果区明确显示“主体范围 + 一次性即时实验”，并提示原始回答仍需回到正式监测证据核对。未指定主体时如实显示账号汇总/未指定，不猜某一家企业。

验证：`npm run check:ui`、`330 passed, 5 skipped`、`git diff --check` 通过；监测对象管理文件保持零差异。

## 139. 2026-09-27 修复开发启动脚本丢失出站身份

Client 报“企业资料暂时读不到 / 出站票的签发声明缺失：private_key_path”时，GEO 进程本身仍在运行，但启动环境没有 `EIOS_AUTH_PRIVATE_KEY_PATH`。因此知识库读取无法签发 AuthContext，资料、覆盖率和补齐建议按设计一起停在保护性空态。

本轮确认 Foundation 开发密钥仍存在且可用，使用 `auth-private.pem`、`auth-public.pem`、issuer、kid、deployment、enterprise 和知识库地址重启 8091；独立探针已验证票签发成功，知识库 8040 返回正常搜索结构。随后把同一组默认配置写入 `scripts/run_dev.sh`，避免之后按项目脚本重启再次丢失身份声明。没有放宽认证，也没有改成无票直连。

验证：`bash -n scripts/run_dev.sh`、`git diff --check` 通过；监测对象管理文件保持零差异。

## 140. 2026-09-27 修复企业资料接口的跨租户固定 ID 冲突

出站身份修复后，企业资料页仍返回“GEO 服务暂时不可用”。直连产品门和日志显示真实原因是 `enterprise_profile_items.id` 的 SQLite 全局唯一约束：当前账号柜为空时，资料路由把固定的系统子项 ID 再写入一次，触发 `UNIQUE constraint failed`，返回 500。

本轮把 48/50 个资料评估子项视为系统模板而非账号记录：当前柜有自定义项时继续读取；当前柜为空时只读复用默认模板，没有默认模板则在内存构造，不再跨账号重复插入固定 ID。这样不会把别的账号资料带进来，也不改变企业资料事实的读取口径。

验证：带真实 Product AuthContext 直连 8091，`enterprise-profile/overview` 与 `enterprise-profile/categories` 均返回 200；目标回归 `32 passed`；`git diff --check` 通过，监测对象管理文件保持零差异。

## 141. 2026-09-28 修正 Foundation 文档导入空态的权限语义

用户反馈“导入企业资料”以前可以从 Foundation 直接选文档，现在列表为空。排查确认当前 Foundation 文档是其他主体的 `personal`、未发布资料，当前登录主体 `human:dev-user` 按文档可见性规则不能读取；GEO 的扫描链路仍然调用 Foundation 的文档读门，没有删除“从 Foundation 选文档”的能力，也没有证据支持跨账号展示这些资料。

本轮没有放宽 Foundation 的可见性、没有添加治理权限、没有复制其他账号的私有文档。后端空态改为明确说明“当前登录账号没有可导入的 Foundation 企业资料”，并提示确认登录账号或在 Foundation 发布/共享资料；扫描响应新增当前账号可见范围说明。前端在导入卡片顶部展示该范围，避免把“当前账号不可见”误报成“知识库没有资料”。

验证：新增空候选权限语义回归测试；UI typecheck/build 通过；`git diff --check` 通过；监测对象管理文件保持零差异。全量测试命令受本地 Foundation 依赖路径未注入影响，出现既有 `eios_policy` / `eios_auth` 模块缺失，非本轮改动导致。
