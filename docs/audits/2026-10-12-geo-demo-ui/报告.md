## 样本与实际修改

- `demo-monitor-samples.ts`：虚构企业“云栖示例家居”，3轮×3问题×4模型，稳定回答/问题/轮次/主体 ID；36 槽位=33 成功回答+3失败，成功回答=28确认提及+2未提及+3主体未知。13正面、5负面、10中立；语气分母28，未知3单列。

- `demo-fixtures.ts`：替换原来互不一致的总览/回答/分析；洞察主题计数、证据抽屉回绑样本 ID 和原话；两项资料缺口、两项行动；资料、认知评分和策略明确为模拟评估，不能当成算法验收。
- 必要的回答页、监测配置、企业总览、认知页和预览卡接线：移除4槽位冒充36条完整样本、各自写死语气/来源/引用数字；演示企业统一为明确虚构名称。
- `geo-monitor-subject.tsx`：演示期间不请求真实对象目录、不改真实主体选择；切回真实模式重新加载目录。回答页不保留演示观察到真实模式。

## 四份盘点及产品问题

静态盘点见[功能接口清单](功能接口清单.json)：20个前端目的地、143条后端路由，其中138条匹配现有产品门允许模式。其余为3条consumer读口、health与knowledge/reset；本轮没有打开任何产品门。该计数来自当前源码，不能用历史矩阵中的路由数量替代，也不代表已验证接口权限或真实连通性。

- 页面：6个一级工作区；监测4个子入口，洞察3个、资料4个、增长6个，另有高级工具。演示下若干入口切换到 `GeoDemoFlowPreview`，不是原业务表单。
- 前置状态：Host Session、启用中的监测主体、已捕获回答、主体解析确认、企业知识可读、内容发布/引用，分别控制不同页面；当前主要依靠各页说明，尚未形成统一的全局准备度模型。
- 数字口径：总览提及覆盖=最近轮次“有提及的问题/有回答的问题”（本样例3/3=100%）；洞察曝光=累计确认提及回答/成功回答（28/33=85%）；语气=13/28正面、5/28负面、10/28中立；推荐=明确编排推荐句13/33=39%；推荐份额=我方推荐/全部品牌推荐，本样例仅我方有推荐句，100%。时间窗与计数单位必须保留，不能要求不同指标数字相等。
- 词表：“经营总览/数据中心”、“认知洞察/差距诊断/品牌理解”、“资料缺口/落后能力点”、“内容计划/行动计划”分别需后续判断合并或区分。`rank_est` 是首次出现的句序，不是推荐排名。

1. 演示预览卡遮住真实业务表单，能审布局，不能审编辑、提交、失败恢复。
2. 9组原话默认折叠；看到结论后还需发现并展开明细入口。
3. 洞察把资料待补项放在“竞品有、我方缺”的容器里；当前交付主题竞品提及为0，仍显示为落后项。样本揭示了容器语义冲突，本轮未改业务判定/信息架构。
4. 模型回答中的“已理解/已连接”等词在隔离测试中只是模拟状态，不能证明真实系统具备它们。
