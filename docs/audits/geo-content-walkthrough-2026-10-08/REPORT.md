## 4. 首个偏离与责任模块

### D01 · Word 上传完整性（真实原文/上传读回比对）

上一跳：现场调研手册包含顶层段落和三张表格。当前跳：`apps/api/app/api/v1/knowledge.py::upload_material` 的 DOCX 分支仅遍历 `d.paragraphs`。输出遗漏表格，而页面显示上传成功，没有说明解析范围。

责任在 GEO 资料解析，不在 Foundation。访谈纪要无表格，能完整上传，后续生成质量问题不能归咎于同一上传缺陷。修复前调查同层 DOCX 解析/切块实现，复用已存在的段落与表格读取能力；不把 Foundation Authority 服务导入 GEO，也不放宽权限。

### D02 · 取材过窄，误报缺资料（真实模型 + 隔离 prompt 证明）

上一跳：正式素材读回包含客户可定制尺寸/颜色/面料、通常 30—45 天交付、当前免费设计、售后与终身维护等访谈表述。当前跳：`services/content::_asset_excerpt` 只通过 `services/embed::best_chunk` 取一段，再截到 400 字；每次只选少量资产。FAQ 的实际同参 prompt 隔离捕获中没有上述关键句。

输出：FAQ 将客户可选择范围、交付细节和设计收费表达为“资料未提供”；第一篇也说访谈没有产品服务展开。**这证明本场景材料在消费接缝丢失，不证明企业确无资料。** 访谈本身仍是企业提供口径，不因此成为正式 Fact。

建议复用现有切块与相关性分数，按子问题取多个有相关性的完整段落，并在总预算内去重；区别“本轮没取到”“资料确未记载”“未经核验”。不要先加向量平台或整篇无脑塞 prompt。

### D03 · 改写资料接缝（真实改写可用，根因是隔离捕获）

真实改写成功不等于来源约束完整。`improve` 已构建 ctx，却只使用 `ctx.materials`；本场景 Knowledge 为空，上传资料位于 `other_assets`。同篇实际输入的隔离捕获显示事实区是“企业知识库里暂无该企业的资料”，并未带上传选段。原稿仍给模型提供部分内容，所以本次能改得像样；不能把此结果说成“改稿一定会忘事实”或“已证明必然编造”。

建议生成与改稿复用同篇解析后的来源/选段，改稿重新核对依据；UI 不能把生成时旧的 context_sources 原样贴在改稿后就当成新稿来源证明。

### D04 · 保存丢来源（浏览器/请求体/正式读回/重启）

保存请求只有 title/content/question，`SaveIn` 也只有这些字段。生成资产读回没有本篇来源；重启后正文仍在，但来源仍缺失。

主责为内容保存 handler、现有素材记录与 UI 投影。store 的 `data_json` 已能保留产品记录元数据，**存在无需新增表的复用候选**；后续先核对验证与兼容边界，不新建 Registry/Ledger，不回填旧稿伪出处。Foundation 正式引用只能保留原合法 ID/version，不自造 Evidence。

### D05 · 资料数和评分遗漏上传来源（真实 UI + 源码）

页面同屏显示“参考资料 0 条”和“历史内容资产（含上传的文件）2 条”；评分 7 分、依据覆盖 0，并建议“只能通用介绍”，而文章已用了上传访谈。根因是 `materials_used` 只统计 Knowledge materials，评分也主要取 Knowledge profile。

建议区分“本篇使用资料”“其中正式事实”和启发式评分覆盖范围。评分未检查的来源不能算没有依据；“发布准备度”不能暗示正文事实已验真。

### D06 · 无依据推断、标题与长度（真实输出）

生成把“调研计划”推成“尚未执行”，FAQ 开头又把用户上传文件称作“公开资料”；原资料不足以证明这两个属性。标题几乎照抄完整指令。选 500 字仍输出明显更长的文章。

建议先修 D02 的输入，再对输出具体主张与来源属性做检查；标题与字数是同条业务链上的输出质量修正，不重构整个产品。不能仅加一句 prompt 就宣布严格事实保证。

## 6. 失败、身份与五层读回

注意旧接口存在 HTTP200+ok:true+data.error 的软失败，不能按 200 统计成功。本轮不支持文件/不存在素材均按实际 error 记录。空内容返回 envelope ok:false。未改变错误合同。

## 7. 后续修改顺序

1. **先修资料解析和取材。** Word 表格完整读取；多子问题取够相关完整段落，避免用“没取到”冒充“没有”。先验收同一份访谈里的定制、30—45天与售后可被正确引用，并保持“据访谈资料”属性。
2. **把同篇资料贯穿改稿与保存。** 使用现有 ctx/切块/data_json；新稿重开有来源，旧稿无来源如实显示。必要的产品字段投影核对兼容，不新增 Authority/schema/第二账本。
3. **纠正计数、评分与输出核验。** 上传资料不再被漏算；调研计划、访谈口径、已验证 Fact 分开；具体主张逐项对原段落，待核验仍保留。
4. **处理时间预算和失败表达。** 在真正运行的 Product API 责任工作树核实范围；耗时分类不改权限 scope。隔离验证慢响应、Provider 拒绝与保存失败的 UI 结果，再有限真实验收。
5. **最后接 Knowledge/Fact。** 手动同步、版本/撤权和正式事实另卡推进，不拿治理未完成阻塞上传资料草稿。

以上为修改建议，尚未执行。普通工程漏接在后续获准范围按纪律连续收口；若涉及未决权限、正式合同语义或新持久化结构，才提交最小裁决。
